    SLIDE 2 — The Problem: SOC Triage is a Human Bottleneck (2:00)¶

    Headline:

    Every QRadar offense is a question that needs an answer¶

    Bullets: - QRadar surfaces raw metadata: rule names, source IPs, event counts - Turning that into a verdict requires an analyst to manually query events, read rule XML, consult runbooks, and cross-reference history - At scale: 30 minutes to several hours per offense - The analyst is the bottleneck — not the detection engine

    The metric that matters:

    Mean Time to Respond (MTTR) is driven by triage time, not detection time.

    Speaker notes:

    "QRadar is excellent at detecting. The problem starts the moment an offense appears in the queue. The analyst opens it and sees a rule name and an IP address. What they need is a verdict — is this real? What happened? What do I do next? Getting there today is a completely manual process. Let me show you what that costs."

    SLIDE 4 — Why Existing AI Solutions Don't Solve It (2:00)¶

    Headline:

    Cloud AI is blocked by the data you can't share¶

    The three blockers: 1. Data egress — offense events contain IPs, usernames, payloads. Sending them to a cloud API violates data residency laws, classified environment policies, and customer data agreements. 2. Air-gapped environments — government, financial, healthcare customers can't reach external APIs at all. 3. Vendor lock-in & cost — pay-per-token pricing on hundreds of offenses per day adds up fast.

    The result:

    Security teams that most need AI assistance are the ones least able to use it.

    Speaker notes:

    "The obvious answer is 'use an LLM API.' But the moment you do that, you're sending your offense events — your source IPs, your usernames, your event payloads — to a third-party server. That's a non-starter for regulated industries. For classified environments, it's simply not possible. I built this with that constraint as a first principle, not an afterthought."

    Visual: A diagram showing the cloud AI data flow with a red "BLOCKED" symbol. Then a second diagram showing on-device inference with a green "COMPLIANT" label.

    SLIDE 7 — Feature: On-Device AI Analysis (3:00)¶

    Headline:

    A structured verdict in 90 seconds — without sending data anywhere¶

    The 5-phase pipeline:

    Phase What happens
    1. Rule XML Fetch Pulls the full detection rule XML from QRadar API — the actual conditions that fired
    2. Event Sampling AQL queries for offense events + source IP timeline (deduplicated)
    3. Historical Context Rule fire frequency, source offense history from local cache
    4. FP Pre-screening R2R directionality, management IPs, reference set exclusions — pre-computed signals
    5. LLM Inference Structured prompt → Qwen3.5-9B → 7-section analysis

    The 7-section output every analyst gets: - VERDICT — True Positive / Likely False Positive / Needs Investigation - Why This Rule Fired — specific rule conditions and signals, not generic text - Severity Assessment — grounded in event volume, magnitude, credibility - Likely Attack Vector — technique + evidence citations - Recommended Immediate Actions — 3–5 specific steps (auto-loaded as response tasks) - False Positive Tuning — exact rule and reference set names to tune - Investigation Steps — forensic steps citing actual IPs, users, payloads

    The number that matters:

    90 seconds vs. 30–120 minutes of manual analysis.

    Speaker notes:

    "The key insight is in Phase 1. Most LLM security tools send the offense description to the model and ask it to guess what happened. We pull the full rule XML — the actual detection logic — and inject it. That's why the output says things like 'this rule fired because the source IP matched reference set XYZ on port 443' instead of 'this appears to be suspicious traffic.' The model has the evidence. It's not guessing."

    SLIDE 8 — Feature: MITRE ATT&CK Mapping (2:00)¶

    Headline:

    Every offense tagged to the kill chain — automatically¶

    How it works: - Nightly scheduled job sends offense + AI verdict to the on-device LLM - Model returns ATT&CK technique IDs - Each ID is validated against a local ATT&CK knowledge base — hallucinated IDs are discarded - Results stored with technique name, tactic, confidence score, and reasoning

    Analyst controls: - Override any AI-assigned technique with the correct one - Promote verified mappings to a shared team knowledge base — QRadar category → ATT&CK technique - Shared mappings improve future auto-tagging for the whole team

    Air-gap support: - ATT&CK bundle can be uploaded manually — no internet access required at tagging time

    Visual:

    Kill chain bar on offense detail: [Reconnaissance T1595] → [Initial Access T1078] → [Lateral Movement T1021]

    Speaker notes:

    "Because every offense is tagged, when you look at a campaign you get the aggregate kill chain across all member offenses. You can see at a glance: this attacker started with reconnaissance, got initial access through valid accounts, and is now moving laterally. That context used to require an analyst to manually correlate. Now it's automatic."

    SLIDE 9 — Feature: Attack Campaign Detection (2:00)¶

    Headline:

    Sophisticated attackers generate many offenses. We connect them.¶

    The problem it solves:

    A persistent attacker generates 40 offenses over two weeks — each one looking isolated when viewed alone. Campaign Detection finds the pattern.

    How detection works: 1. Build an adjacency graph: offenses connected by shared detection rules OR shared attacker source 2. BFS walk finds connected components — clusters of related offenses 3. Filter: minimum 3 offenses to form a campaign 4. Compute: kill chain progression, severity, analyst assignments, lateral movement flags

    What you see: - Named campaign with kill chain progression bar - [Recon] → [Initial Access] → [Lateral Movement] - ⚠ Lateral movement warning when hop chains are confirmed - All member offenses linked in one view

    Key property:

    Pure graph computation — no LLM. Fast, deterministic, runs nightly automatically.

    Speaker notes:

    "This is one of my favorite parts of the platform. Campaign detection doesn't need the LLM at all. It's a BFS on a graph where edges represent shared rules or shared attacker sources. It runs in seconds and it finds patterns that are genuinely invisible when you're looking at one offense at a time. The lateral movement detection is particularly powerful — it compares the destination IPs of one offense's events against the source IPs of the next offense, which is a direct signal of a hop chain."

    Visual: Screenshot of campaigns-list.png and campaign-detail.png.

    APPENDIX¶

    Appendix A — Detailed Technical Q&A Prep¶

    Q: Why Qwen3.5-9B and not a larger model?

    9B parameters at Q5 quantization is 6.1 GB — it fits in the 8 GB container allocation with headroom. It produces quality analysis in 60–90 seconds on CPU. A larger model (e.g. 70B) would require 20–40 GB and take 10–20 minutes per inference, making the analyst experience unacceptable. Qwen3.5 specifically was chosen for strong instruction following and structured output compliance.

    Q: What happens if the LLM produces a wrong verdict?

    The verdict is a recommendation, not an automated action — the analyst makes the final call. False positive pre-screening (Phase 4) grounds the verdict in pre-computed signals so the model isn't making unsupported claims. Analyst override is always available. In practice, the value is in the 90-second analysis vs. 30-minute manual triage — even an imperfect AI verdict that directs investigation correctly is a massive throughput improvement.

    Q: How are campaign IDs stable across re-runs?

    Campaign ID is the MD5 hash of the sorted set of member offense IDs. Same members = same ID. If a new offense joins the cluster, the ID changes — by design, signaling the campaign has evolved. This makes campaigns trackable in reporting systems and safe to use as foreign keys.

    Q: What is the inference timeout and can it be tuned?

    Default is 600 seconds. On slower hardware (older QRadar appliances with fewer CPU cores), token generation may be under 1 token/second. The timeout is configurable under Settings → System Settings → AI Inference Timeout. 900 seconds is recommended for CPU-only deployments on constrained hardware.

    Q: Does this work on multi-host QRadar deployments?

    The app container runs on the QRadar Console. AQL queries and rule XML fetches go through the standard QRadar API, which handles multi-host event routing transparently. The app doesn't need to be aware of managed host topology.
